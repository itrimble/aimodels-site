StrixFold measured two Bosgame M5 pairs and a pair of Ryzen AI Halo boxes over USB4. TensorFold measured a single Strix Halo on ROCm. Measured

StrixFold is the two-box HIP fork of TensorFold; its rows are third-party measurements on Bosgame M5s. Our pair results use llama.cpp RPC over Thunderbolt. TensorFold rows are its ROCm benchmark receipts on a single Strix Halo.

Method: Rows marked 'ours' are our own runs on Bosgame M5 systems, with the llama-bench run receipt linked as the source. All other rows are measured results from published sources, not our own benchmarks. decode_tok_s is token generation speed; prefill_tok_s is prompt processing; ttft_s is time to first token. Context matters: a result at 4K is not a result at 128K. A missing prefill cell means the source did not report it, not that it is zero. Machine-readable: data/benchmarks.json.

Prefill and decode

Prefill is how fast the model reads the prompt; it sets the time to first token and the cost of a long context. Decode is how fast it writes the answer; it sets sustained output. They are separate measurements, and a single “tokens per second” number without a label is ambiguous.

StrixFold reports both, so its M5 rows have both columns. TensorFold’s issue #1001 reports stream-delivery decode only; its prefill cells are n/a because the source did not measure them. That is a missing measurement, not a zero. The same applies to the coding and 8K rows from Strata.

Measured vs estimated

A green Fits on the fleet matrix is a memory-fit verdict, not a speed claim. The ≈ tok/s ceiling under it is bandwidth divided by active weight bytes. A model can fit and still be unpleasant at 4 tok/s; the 27B BF16 row is the obvious example. The measured table above is what happened on real hardware.

The benchmark plan

Run the same commands on both boxes, at the same context, with the same build. Record the command, the model revision, the driver or ROCm version and the room temperature; a number without those is not a benchmark. The one-M5 commands below produced the strix1 rows; the receipt records the build, ROCm and kernel, and says what was not recorded (room temperature, power).

# One M5, after the one-box set is copied
llama-bench -m /models/official/unsloth-Qwen3.8-Flash-Next-UD-IQ4_XS/UD-IQ4_XS/Qwen3.8-Flash-Next-UD-IQ4_XS-00001-of-00004.gguf -p 512 -n 128 -ngl 99 -r 3

# Same build, longer prompt; this is where KV cache and prefill show up
llama-bench -m /models/.../Qwen3.8-Flash-Next-UD-IQ4_XS-00001-of-00004.gguf -p 8192 -n 128 -ngl 99 -r 3

# Two boxes, after rpc-server is running on box B
rpc-server -H 192.168.12.72 -p 50052
llama-bench -m /models/.../DeepSeek-V4.1-Flash-1017-GSQ-RCO-IQ1_M-00001-of-00006.gguf --rpc 192.168.12.72:50052 -p 512 -n 128 -ngl 99 -r 2

Measure load time separately. The first token after a 16K prompt is not the same as steady-state decode, and a two-box result should report the link and the split.

What this page is not

  • Not only ours: rows marked ours link our raw run; every other row links to the person or project that measured it.
  • Not a quality score. Speed says nothing about answer quality.
  • Not a comparison across different prompts. The context column is part of the number.
  • Each local result identifies the machine and backend used for that run.
